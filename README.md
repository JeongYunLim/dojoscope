# DojoScope — Trace Behavior Atlas (server 버전)

AgentDojo 프롬프트 인젝션 벤치마크의 실행 기록(trace)을 "판정(성공/뚫림)"이 아니라
**행동의 궤적**으로 비교하기 위한 시각적 분석 도구다. 업로드한 trace JSON을
서버가 즉시 파이프라인(임베딩 → DTW 시퀀스 거리 → GT 정렬/잔차 → UMAP → 계층적
군집화 → 통계 검증)으로 재계산하고, 브라우저는 그 결과를 raw/residual 듀얼
지도와 **임의의 두 케이스를 직접 DTW로 비교하는 도구**로 보여준다.

계산 파이프라인(`backend/pipeline/`)은 기존 `dojoscope-trace-viz` 프로젝트의
검증된 구현(단위 테스트 포함)을 그대로 재사용한다 — 이벤트 벡터화, DTW, GT 정렬,
UMAP, 계층적 군집화(ARI/NMI 검증)의 방법론은 해당 프로젝트의 README를 참고.

## 이번 버전에서 새로 만든 것

1. **실제 서버(FastAPI)** — 이전 버전은 "서버 없이 정적 파일만" 접근 안정성을
   위해 서버를 걷어냈지만, 이번 요청은 "데이터 파일을 업로드하면 그 데이터에 맞춰
   서버가 돌아가야" 하므로 업로드 → 병합 → 재계산 → 서빙을 처리하는 FastAPI
   앱(`backend/app.py`)을 새로 만들었다.
2. **완전히 새로 설계한 화면** — 좌측 속성/필터 패널, 중앙 residual UMAP(기본
   뷰) 지도, 우측 raw UMAP ↔ 거리 행렬 탭 + 군집 검증, 하단 트레이스 직접 비교
   도구로 구성된 4분할 레이아웃(첨부 스크린샷의 "좌측 속성 · 중앙 지도 · 우측
   임베딩맵 · 하단 패널" 구조를 이 도메인에 맞게 재해석).
3. **임의의 두 케이스를 직접 DTW로 비교하는 도구** — 기존 버전은 같은
   (user_task, injection_task) 쌍의 A/B만 비교할 수 있었다. 이번 버전은
   `/api/compare`가 **어떤 두 케이스든** 즉석에서 벡터화 + DTW 정렬해서 거리와
   정렬 경로를 돌려준다. 화면에는 DTW 거리 숫자, 정답(GT)/트레이스A/트레이스B
   3단 정렬 스트립, 그리고 **정렬 스텝을 이동하는 스크러버**(슬라이더 · 재생
   버튼)가 있어 세 시퀀스를 같은 스텝 축 위에서 동시에 훑으며 비교할 수 있다.
4. **거리 행렬(클러스터 히트맵)** — "지도만 봐서는 각 트레이스 간 DTW 거리를 알 수
   없다"는 문제에 대한 답. 우측 패널 "거리 행렬" 탭이 모든 케이스 쌍의 잔차 DTW
   거리를 계층적 군집 병합 순서로 정렬해 히트맵으로 보여준다(Munzner 7.5.2
   Cluster Heatmap 패턴). 셀을 클릭하면 그 두 케이스가 바로 아래 비교 도구의
   A/B로 채워진다.
5. **오버뷰 → 탐색** — raw/residual 두 지도 모두 브러시 드래그로 영역을 선택하면
   평균 잔차 길이·주도 납치 도구·판정 분포가 즉시 요약되고, 점에 마우스를
   올리면 두 지도에서 같은 케이스가 함께 강조된다(linked highlighting). 좌측
   속성 뷰의 막대(판정/납치 도구/지연)를 클릭해도 같은 방식으로 필터링되고, 그
   조건에 맞는 케이스 목록이 그대로 나열되어 클릭 한 번으로 비교 도구에 올릴 수
   있다("속성 뷰에서 선택한 걸 바로 확인" 요구사항).
6. **AgentDojo 실 로그 어댑터** (`backend/adapters/agentdojo_adapter.py`) —
   ethz-spylab/agentdojo의 실제 `TraceLogger` 출력 형식(§ "실 로그 사용하기" 참고)을
   우리 스키마로 변환한다.
7. **트레이스 원문 보기** — 지도/거리행렬/속성뷰 목록/군집 대표 사례 중 아무거나
   클릭해 A(또는 B)로 고르면, 하단 "트레이스 비교" 안에 그 케이스의 **원문 이벤트
   전체**(역할, 도구 이름과 인자, 응답 텍스트, GT매칭/잔차/주입됨 표시)가 펼쳐진다.
   두 케이스를 다 고르면 탭으로 A/B 원문을 오가며 볼 수 있다.
8. **케이스별 방어 전/후 한 번에 불러오기** — 트레이스 원문 패널의 "↔ 방어 전/후
   짝 케이스 불러오기" 버튼이 같은 (suite, user_task, injection_task)의 다른 조건
   케이스를 찾아 A/B에 자동으로 채우고 비교까지 실행한다 — 지도에서 아무 점이나
   눌러도 바로 그 트레이스의 방어 전/후를 확인할 수 있다.
9. **집계 수준 "방어 전/후" 요약** — `security_analysis`(Targeted ASR, McNemar
   검정, 안전 완료율)는 이미 파이프라인이 계산해 두고도 화면에 없던 데이터였다.
   새 "보안 결과" 패널에 조건별 ASR(95% CI 포함), A→B 짝 비교(차단/퇴행/여전히
   뚫림/여전히 안전 4분면 + McNemar p-value)로 노출했다.
10. **군집 대표 사례(medoid) 노출** — `pipeline_study`가 도입한 medoid 개념을
    화면에도 반영: 지도 위 ★ 표시 + 좌측 목록(군집 번호·크기·대표 납치 도구)으로
    "이 군집을 한 케이스로 요약하면?"에 바로 답한다. 클릭하면 그 케이스가 A로
    선택된다.
11. **Control Panel 이동 가능** — 제목줄을 드래그하면 어디로든 옮길 수 있다(더
    이상 지도 위 점을 가릴 걱정 없이 빈 자리로 치워둘 수 있음).
12. **군집 개수(k)를 직접 조절** — 서버가 라벨 없이 실루엣만으로 자동 선택한 k는
    banking suite에서 2로 나와("가장 굵직한 구분"만 남기는 쪽이 실루엣 점수가
    가장 높았기 때문) 실제로 군집이 왜 이렇게 적냐는 질문을 받았다. 원인은
    알고리즘이 아니라(여전히 계층적 군집화·average linkage 그대로) 자동
    k 선택이 지나치게 보수적이었던 것 — Control Panel에 **군집 윤곽 개수(k)
    슬라이더**(2~20)를 추가해 서버가 이미 보내준 덴드로그램 병합 기록
    (`distance_matrix.residual_merge_log`)을 **클라이언트에서 즉시 잘라
    재계산**한다(서버 왕복 없음).
13. **점 색상/모양과 군집 표시를 완전히 분리** — 처음엔 "색상 기준=계층적 군집"
    을 골라야 군집이 보이게 했는데, "색상은 과제 성공/실패, 모양은 방어 O/X로
    고정해 두고 군집은 윤곽선에만 색을 주면 되지 않냐"는 피드백을 반영해 구조를
    바꿨다. 이제 **점 색상·모양은 항상 과제 성공/실패(색) · 방어 O/X(모양)로
    고정**되고, **군집은 지도 위 점선 윤곽선에 별도 팔레트로 항상 표시**된다
    (점 색과 혼동하지 않도록 Okabe-Ito가 아닌 별도 색상 세트 사용). 색상 기준
    드롭다운에서 "계층적 군집" 옵션 자체를 없애 더는 이 둘을 오갈 필요가 없다.
14. **군집 특성 패널(항상 표시)** — residual 지도 아래에 군집마다 크기·주도
    납치 도구·뚫림 비율·평균 잔차 길이를 표로 보여준다(PPT가 손으로 했던
    "이 군집엔 어떤 케이스가 몰려 있나" 분석을 화면에서 바로 확인), 표의 색
    스와치는 지도 윤곽선과 같은 색이라 바로 대응된다. 행을 클릭하면 그 군집의
    대표 사례(medoid)가 비교 도구에 열린다.
14. **호버 팝업이 안 사라지던 버그 수정** — 점을 클릭하면 지도가 다시 그려지며
    호버 중이던 점의 DOM 요소가 사라지는데, 그 바람에 `mouseleave`가 발생하지
    않아 툴팁이 화면에 계속 남아 있던 버그를 고쳤다(재렌더링 시작 시 항상
    툴팁을 먼저 닫도록 수정).

15. **다중 뷰 대시보드로 재구성(모달 → 상시 패널)** — 스크롤 없이 한 화면에
    담으려고 트레이스 비교/보안 결과를 클릭 시 여는 오버레이(모달)로 옮긴 적이
    있었는데, "DRTLens류 대시보드처럼 UMAP VIEW 옆에 TRACE VIEW·ANALYSIS VIEW가
    나란히 있고, 지도에서 트레이스를 고르면 바로 그 옆 패널에 반영되면 좋겠다"는
    피드백을 반영해 **모달을 없애고 처음부터 화면에 상시 떠 있는 패널**로
    바꿨다. 레이아웃은 2행 그리드: 1행 = 속성 지도(residual, 기본)·궤적
    지도(raw/거리행렬), 2행 = **TRACE VIEW**(선택한 A/B 케이스의 원문 이벤트) ·
    **ANALYSIS VIEW**(DTW 거리·GT 3단 정렬·스크러버·진단 + 조건별 보안 결과
    집계). 좌측 속성 뷰는 두 행에 걸친 세로 사이드바. 지도의 점, 군집 대표
    사례, 속성뷰 필터 목록, 거리 행렬 셀, 방어 전/후 짝 버튼 — 무엇을 클릭해도
    TRACE VIEW·ANALYSIS VIEW가 즉시 갱신되고, 지금까지 열어본 A/B 조합은
    **◀ 이전 / 다음 ▶** 방문 기록으로 오갈 수 있다(팝업이 아니라 항상 보이는
    패널이라 "안 사라지는 팝업" 같은 문제 자체가 생길 수 없다).

16. **학술 논문에 쓸 수 있는 화면으로 재설계** — "AI가 만든 느낌"(흰 배경,
    루시드류 아이콘, 무분별한 그림자, 이모지, 무지개 팔레트, 긴 대시, 뻔한
    산세리프 폰트, 둥근 모서리 등)을 걷어내고 학술 소프트웨어 관례를 따랐다:
    종이 톤 배경, `border-radius`/`box-shadow` 전면 제거(사각형), 이모지·장식
    기호 제거, 화면에 보이는 em-dash를 마침표/쉼표로 교체, 4개 상시 패널에
    논문 다중 패널 그림처럼 (a)(b)(c)(d) 표지를 달았다. 폰트는 처음에 세리프
    학술 폰트로 바꿨더니 이 밀도의 UI에서는 줄바꿈이 깨지며 레이아웃이
    무너지는 걸 확인해서(세리프는 본문 산문용이지 조밀한 대시보드 위젯에는
    안 맞음), 장식 없는 시스템 산세리프로 되돌렸다.
17. **빈 상태 → 업로드 흐름의 실제 버그 수정** — 데이터가 없을 때 안내 카드가
    화면 중앙이 아니라 다른 위치에 떠 보이던 버그를 발견해, 빈 상태일 때는
    뒤에 깔린 `#layout`을 아예 `display:none`으로 숨기도록 고쳤다(이전에는
    빈 패널들이 배경에 계속 렌더링되면서 레이아웃 계산에 간섭했다).
18. **UMAP·군집화 결과 재검증** — "예전과 달라 보인다"는 문제 제기를 받고 직접
    다시 계산해 확인했다: ① UMAP 좌표는 서버를 몇 번을 재시작해도
    `banking__user_task_0__injection_task_0__A` 기준 `[7.3045, 8.9819]`로
    소수점까지 동일함을 재확인했고(§ 아래 "UMAP 좌표가..." 절의 `n_jobs=1`
    수정이 여전히 유효함), ② 클라이언트에서 군집 개수(k) 슬라이더로 즉석
    재계산하는 `dendrogramCut()`(JS)이 서버의 `cut_into_k_clusters()`(Python,
    `pipeline/cluster.py`)와 k=2,3,4,6,10,15 전부에서 **완전히 동일한 라벨**을
    내는 것을 실제로 두 언어 구현을 나란히 실행해 대조했다. 즉 계산 자체는
    이전과 달라진 게 없고 정확하다 — 달라 보인 이유는 k 슬라이더의 기본값이
    6인 반면 서버가 라벨 없이 자동으로 고른 참고 k는 suite마다 다르기(예:
    banking은 실루엣 기준 k=2) 때문에, 이전에 본 화면과 군집 개수 자체가
    달라서 그렇게 보였을 가능성이 크다.
19. **색상: 4장이 아니라 10장(Map Color and Other Channels)을 다시 적용** —
    danger/safe 색(#a13a2f/#2e6b4f)의 **상대 명도를 직접 계산**해보니 대비비가
    1.05:1로 사실상 흑백에서 구분이 안 됐다(Munzner 6.9 "Get It Right in
    Black and White" 위반 — 10장이 색 채널을 다룰 때 거듭 참조하는 규칙).
    danger=#7a2a20, safe=#4d9c76로 바꿔 대비비를 2.91:1로 끌어올렸다(danger는
    배경과 9.39:1, safe는 배경과 3.23:1). 나머지 색 결정은 10장 기준으로
    재점검해 이미 맞게 되어 있음을 확인했다: 범주형 팔레트는 6~12개 구간
    권장(Okabe-Ito 8색/ColorBrewer Dark2 8색 모두 충족), 순서형 데이터(거리
    행렬)는 단일 색상 sequential 컬러맵(Blues), ARI 발산 막대는 0을 중심으로
    두 색이 갈라지는 diverging 인코딩, 큰 면적(군집 윤곽 채우기)은 낮은
    채도·작은 선(윤곽선 자체)은 상대적으로 진한 색.

20. **1~10장 전체를 기준으로 한 재점검** — 이번엔 색(10장)만이 아니라 1~10장
    전체를 처음부터 끝까지 다시 읽고, 그 기준으로 화면을 다시 점검해서 실제로
    고친 부분:
    - **범주형 색상 팔레트가 배경에서 사실상 안 보이던 문제** — Okabe-Ito의
      순노랑(#F0E442)과 ColorBrewer Dark2의 노랑(#e6ab02)을 배경(#f2f0ea)에
      직접 대비비로 계산해보니 각각 1.16:1, 1.81:1로 6.9 "Get It Right in
      Black and White"에 어긋났다(원래 이 두 팔레트는 흰 배경/어두운 배경을
      가정하고 만들어졌지 이 프로젝트의 크림색 종이 배경을 가정한 게 아니다).
      같은 색상족을 유지한 채 톤만 낮춰 겨자색(#7d6608, 4.88:1)·올리브
      (#8a6a1f, 4.43:1)로 교체했다(`frontend/app.js`의 `OKABE_ITO`,
      `CLUSTER_HULL_PALETTE`).
    - **범주형 팔레트가 넘칠 때 색이 조용히 겹치는 문제** — `d3.scaleOrdinal`은
      도메인이 팔레트 길이(8색)를 넘으면 색을 재사용해서 서로 다른 범주를 같은
      색으로 오인코딩한다. 지금 샘플/예시 데이터는 hijack_tool 등이 1~3종류뿐이라
      드러나지 않지만, 실 AgentDojo 로그는 공격 대상 도구가 8종을 넘을 수 있어
      잠재적 버그였다. `colorScaleFor()`에 초과 감지를 넣어 콘솔 경고 + 범례에
      "색이 겹침" 표시를 하도록 했다(6.9 위반을 조용히 넘기지 않고 드러내기).
    - **9장(Arrange Networks and Trees) 기준 거리 행렬 정당화** — 거리 행렬을
      matrix가 아니라 node-link 그래프로 그리지 않은 이유를 9.4의 비용/이득
      분석 그대로 캡션에 명시했다: 케이스 n개 사이에 거리가 전부(n(n-1)/2건)
      존재하는 완전 그래프라 node-link로 그리면 edge 밀도가 가독성 한계
      (node 수의 약 4배)를 훨씬 넘어 hairball이 되지만, matrix는 occlusion
      없이 조밀한 그래프까지 선형적으로 확장되고 레이아웃이 안정적이다. 대신
      matrix가 약한 "경로 추적" 과제는 (c) TRACE VIEW의 직접 A/B 비교로
      보완한다는 트레이드오프도 캡션에 남겼다.
    - **8장(Arrange Spatial Data) 기준 재확인** — UMAP 좌표는 "주어진(given)"
      공간 데이터가 아니라 차원축소로 "유도된(derived)" 배치이므로 8장의
      규칙이 아니라 13장의 차원축소 의미론이 적용된다는 점을 재확인했다.
      두 지도 모두 "축에는 절대값이 없다"는 캡션을 이미 달고 있어 이 구분을
      이미 정확히 반영하고 있었다(수정 불필요, 확인만).
    - **7장(reorderable matrix) 재확인** — 거리 행렬의 행/열 순서가 업로드
      순서가 아니라 계층적 군집 병합 순서(`leafOrder`)로 재정렬되어 있는지
      코드로 직접 확인했다 — 이미 올바르게 구현되어 있었다(수정 불필요).
    - 이 항목은 "10장만 다시 보고 색만 고친" 이전 패스와 달리, 1~10장
      전체(데이터 추상화·과제 추상화·검증·마크와 채널·규칙·표 배치·공간 데이터·
      네트워크와 트리·색)를 순서대로 다시 읽고 각 장이 실제로 이 프로젝트의
      어느 화면 요소에 해당하는지 하나씩 대조한 결과다.

21. **"군집 6개인데 1개로 뭉쳐 보인다" 버그 — 알고리즘이 아니라 확대(줌) 부재가
    원인이었다** — 실제로 `dendrogramCut()`을 k=6으로 콘솔에서 직접 돌려보면
    6개 라벨(1/14/5/9/8/11건)이 정확히 나뉜다. 문제는 residual DTW 거리가
    대부분 0에 가깝고(동일 템플릿 트레이스가 많아서) 소수의 이상치만 멀리
    떨어져 있다 보니, 전체를 다 보여주는 고정 축 범위(overview)에서는 정상
    케이스 대부분이 몇 픽셀짜리 점 뭉치로 짜부라져 hull 5개가 서로 겹쳐 한
    덩어리처럼 보였던 것 — `getBBox()`로 hull 크기를 직접 재보니 실제로
    7~22px 크기였다. 좌표를 임의로 잘라내면 데이터를 왜곡하게 되므로(6.9),
    11장(Manipulate View → 11.5 Navigate: Changing Viewpoint)의 지침대로
    스크롤 확대/축소(`d3.zoom`, 배율 1~40배 제한 — 11.5.3 constrained
    navigation)와 "화면 맞춤" 리셋 버튼을 추가해 밀집 영역을 확대해서 볼 수
    있게 했다(`frontend/app.js`의 `attachZoom`/`resetZoom`, `renderMap`이
    이제 `mapZoomTransform`으로 x/y 스케일을 `rescaleX`/`rescaleY`한다).
    좌클릭 드래그는 기존 브러시 선택에 그대로 남겨두고 휠 스크롤에만
    줌을 배정해 두 제스처가 충돌하지 않게 했다.

22. **Control Panel이 지도를 가리던 문제 — 뜬 패널을 없애고 좌측 사이드바로
    이동** — 드래그 가능한 플로팅 패널은 처음 열었을 때 항상 지도 중앙을
    가려서(스크린샷으로 직접 확인) 점을 보기도 전에 옮겨야 했다. 패널을
    없애고 그 안의 컨트롤(점 크기·군집 윤곽 개수 k·이상치 강조·군집 윤곽
    표시·군집 대표 사례 표시)을 좌측 속성 뷰 사이드바의 "지도 설정" 섹션으로
    옮겼다 — 데이터 마크 위에 UI를 겹쳐 올리지 않는 편이 원칙적으로도
    맞다(지도는 데이터를 보여주는 공간, 컨트롤은 별도 패널이라는 역할
    분리는 12장의 juxtapose된 다중 뷰 구성과도 맞다).

23. **보안 관제 대시보드 템플릿(shadcn-admin, Tremor, Tabler, Wazuh 등) 조사 후
    패턴만 이 프로젝트 스택(바닐라 JS+D3, React/Tailwind 아님)에 맞게 재구현** —
    GitHub/공식 문서를 직접 찾아본 결과 세 축의 공통 패턴을 확인했다: (1) 상단
    KPI 카드 행, (2) Critical/High/Medium/Low 심각도 배지, (3) 필터·페이지네이션이
    있는 이벤트 로그 테이블. "실시간 트래픽 시계열"은 별도로 찾아보지 않고
    구현하지 않았다 — AgentDojo trace에는 실제 벽시계 타임스탬프가 없어서
    "실시간"인 것처럼 보이는 차트를 넣으면 데이터 성격을 왜곡하게 된다(6.9
    Get It Right in Black and White는 색뿐 아니라 이런 종류의 오도에도 적용된다).
    - **KPI 카드**(`#kpi-bar`, topbar 바로 아래) — 전체 케이스·Critical·High·
      Medium·Low 건수·B조건 방어 성공률 6개를 항상 먼저 보여준다(6장 "Overview
      First"). "현재 필터 기준" 스냅샷이라고 명시해 실시간 텔레메트리로
      오인되지 않게 했다.
    - **심각도(severity) 4단계** — 이 프로젝트에 실제로 있는 필드(`security`
      뚫림 여부·`condition` 방어 유무·`utility` 과제 성공 여부)를 조합해
      Critical(방어 있었는데도 뚫림)/High(무방어 상태에서 뚫림)/Medium(안 뚫렸지만
      과제 실패)/Low(정상)로 정의했다(`app.js`의 `severityOf()`). 심각도는
      순서가 있는(ordinal) 속성이므로 임의의 질적 색상이 아니라 위험도가 오를수록
      진해지는 4단계 단일 색조 램프를 썼다(10.3 sequential colormap, 배경 대비
      전부 4.4:1 이상 — 직접 계산해 확인). 좌측 "심각도 분포" 미니 차트, 색상
      기준 드롭다운의 "심각도" 옵션, 이벤트 로그의 배지 세 곳에서 같은 색 매핑을
      공유한다(12장 Share Encoding).
    - **이벤트 로그 테이블**(`#event-log-section`) — 심각도 배지·필터 칩
      (전체/Critical/High/Medium/Low)·case_id 검색·20건 단위 페이지네이션을
      갖춘 테이블. 행을 클릭하면 기존 TRACE VIEW/ANALYSIS VIEW로 그대로
      연결된다(이미 있던 `pickedA`/`afterPickChange` 경로를 재사용) — 새 뷰를
      고립시키지 않고 기존 다중 뷰 구성에 연결한 것이다.

24. **이벤트 로그가 스크롤해야 보이던 문제 — 그리드 3번째 행으로 편입해 한
    화면에 전부 보이게 함** — 처음엔 이벤트 로그를 DRTLens 그리드(4패널, 고정
    뷰포트) 바깥에 둬서 페이지를 내려야 보였는데, "위에 보낸 예시 이미지들처럼
    데이터가 한눈에 다 보였으면 좋겠다"는 피드백을 받았다. `#layout`의
    `grid-template-rows`를 `1.15fr 1fr`(2행)에서 `1.05fr 0.85fr 200px`(3행)로
    바꾸고 이벤트 로그를 3번째 행(전체 폭, `(e)` 표지)으로 넣어 나머지 4개
    패널과 함께 한 뷰포트 안에 항상 보이게 했다. 표 안에 몇 건이 있을지는
    미리 알 수 없으므로, 페이지 전체가 아니라 `.event-log-table-wrap`
    (`flex:1; min-height:0; overflow-y:auto`) 하나만 내부 스크롤하게 해서
    표가 아무리 길어도 그리드 행 높이(200px)를 벗어나지 않는다. 브라우저에서
    `document.documentElement.scrollHeight`(901px)와 `window.innerHeight`
    (900px)를 직접 재서 페이지 레벨 스크롤이 실질적으로 없어졌음을 확인했다.

25. **"내용을 보려고 계속 스크롤해야 한다" — 보안 개발자 페르소나로 직접
    써보면서 각 패널 안쪽까지 점검, 5개 패널 전부 스크롤 없이 보이게 재구성**
    — 24번 항목은 이벤트 로그가 페이지 밖으로 밀려나는 것만 고쳤을 뿐,
    5개 패널 각각의 **안쪽**은 여전히 넘쳐서 패널별로 스크롤해야 했다.
    `el.scrollHeight`와 `clientHeight`를 모든 패널에서 직접 재서(스크립트로)
    실제 초과분을 숫자로 확인한 뒤 고쳤다 — "달라 보인다"가 아니라 "몇 px
    넘치는지" 재고 고치는, 이 프로젝트에서 계속 써온 방식 그대로다.
    - **속성 뷰(좌측 사이드바) 714px 초과 → 33px 로 축소**: "표시 케이스"
      숫자 카드는 KPI 바·배지와 이미 세 번 중복이라 **삭제**했고, O/X 인코딩
      설명 문구는 범례에 이미 있는 문장이라 **삭제**했다. 색상/크기 기준
      드롭다운을 2열로, 지도 설정의 슬라이더·체크박스를 2열/한 줄로
      합쳤다. 심각도·판정 미니 차트는 한 행에 나란히(2열), 상대적으로 덜
      중요한 지연 버킷 차트는 "더보기"로 접었다 — 트리아지 중엔 안 보게
      된다는 걸 실제로 써보고 판단했다.
    - **속성 지도/궤적 지도 패널**: 캡션 문장을 짧게 줄이고(근거는 README에
      이미 있으니 화면에서는 요지만), 군집 검증표(`cluster-validation`)는
      hijack_tool 행만 기본 표시하고 나머지 속성(user_task_id/exposure_channel
      /delay_bucket/verdict)은 "다른 속성 기준 검증 더보기"로 접었다 —
      hijack_tool ARI가 이 프로젝트 전체에서 반복 인용되는 핵심 지표이고
      나머지는 데이터 위생 점검용 부가 지표라는 걸 실제 사용 흐름에서
      확인했다.
    - **TRACE VIEW/ANALYSIS VIEW**: 트레이스 원문과 DTW 정렬 결과는 케이스마다
      길이가 들쭉날쭉해서(이벤트 3개짜리도 50개짜리도 있음) 무조건 한 화면에
      다 넣을 수는 없다 — 대신 A/B 선택기와 DTW 거리 헤더는 항상 고정해 두고
      `trace-detail-body`/`#compare-body` **안쪽만** 스크롤되게 했다(패널
      전체가 아니라). 그래야 긴 트레이스를 내리는 동안에도 "지금 뭘 보고
      있는지"를 놓치지 않는다. 보안 결과 집계(`security-details`)는 기본
      접어 두고 펼치기 전에도 "ASR A 73% → B 21%" 한 줄 요약만 보이게 했다
      (예전엔 기본으로 펼쳐져서 607px를 차지했다).
    - **버그 두 개를 이 과정에서 발견**: (1) `#panel-center`에 `overflow-y`가
      아예 설정돼 있지 않아서(`visible`) 내용이 넘치면 패널 밖으로 그대로
      새어나가 아래 행과 겹칠 수 있었다 — `getComputedStyle().overflowY`로
      직접 확인 후 다른 패널처럼 `auto`로 통일했다. (2) flex 세로 컨테이너
      안에서 `overflow:auto`를 준 자식은 CSS 스펙상 automatic minimum size가
      0이 돼서, 공간이 살짝만 모자라도 내용이 통째로 사라지는 버그가
      있었다(`cluster-summary`, `trace-detail-body`, `#compare-body`에서
      실제로 재현 — `clientHeight`가 0~5px까지 찌부러짐). `min-height`를
      명시해 바닥을 깔아 막았다.
    - 최종적으로 1440×900 기준 문서 스크롤은 901px/900px(사실상 없음),
      5개 패널 모두 헤더·컨트롤이 항상 보이는 상태에서 내용이 많을 때만
      해당 위젯 **안쪽**이 스크롤되도록 확인했다.

26. **설명 가능성(XAI)을 이 프로젝트의 핵심 전제로 삼아 "왜 이렇게 판단했는지"를
    문장이 아니라 실제 계산값으로 보여주는 위젯 추가, 나머지 설명 문구는 축약**
    — 이 프로젝트가 신뢰받으려면 UMAP·군집화가 "이 케이스들이 비슷하다"고
    말할 때 그 근거를 사람이 검증할 수 있어야 한다는 요구를 반영했다. 두
    가지를 구분해서 처리했다:
    - **군집/유사도 판단 근거 — 최근접 이웃 위젯** (`renderNeighborEvidence()`,
      ANALYSIS VIEW) — 케이스를 하나 고르면 그 케이스와 residual DTW 거리가
      가장 가까운 4건을 실제 거리값과 함께 막대로 보여준다. "UMAP이 이걸
      묶었다"는 주장을 문장으로 정당화하는 대신, 애초에 군집화가 사용한
      바로 그 거리 행렬(`distance_matrix`, 이미 거리 행렬 히트맵에도 쓰던
      데이터)에서 이웃을 직접 뽑아 보여줘서 — 그 케이스가 왜 이 근처에
      있는지 사람이 숫자로 재현/검증할 수 있다. 막대를 클릭하면 그 이웃이
      바로 B로 들어가 DTW 정렬까지 확인할 수 있다.
    - **심각도 판단 근거** — Critical/High/Medium/Low는 원래부터
      `severityOf()`(hijack 여부·조건 A/B·과제 성공 여부 3가지 불리언 조합)로
      정해지는 규칙 기반 라벨이라 애초에 블랙박스가 아니다. 다만 이걸 문장으로
      설명하던 걸(이번 턴에서) 없애고 이벤트 로그·지도 범례의 색상 배지 하나로
      대체했다 — 규칙 자체는 README에 근거를 남기고, 화면에서는 데이터(배지
      색)로만 전달한다.
    - **설명 문구 추가 축소** — 지도 캡션·툴팁·범례 노트 등 남아 있던
      문장들을 다시 훑어 단어 단위로 줄였다(예: 거리행렬 캡션 2문장→반문장).
      수치·차트로 이미 전달되는 내용을 문장으로 반복하지 않는 걸 기준으로
      삼았다.

27. **레이아웃을 2×2 패널로 단순화하고, 흰 배경·Pretendard로 바꾸고, 색
    채널 전체를 Ch10(Map Color and Other Channels) 기준으로 다시 계산** —
    사용자가 첨부한 와이어프레임(케이스 개수/critical/high/medium/low/방어
    성공률 KPI 행 + (a)속성지도 (b)trace 원문 (c)이벤트 로그 (d)analysis view
    2×2 배치)에 맞춰 기존 5패널(속성 뷰 사이드바 + residual/raw 지도 분리)
    구조를 다시 짰다.
    - **레이아웃**: 왼쪽 사이드바(속성 뷰)를 없애고, residual/raw UMAP과
      거리 행렬을 `(a) 속성 지도` 패널 하나 안의 탭(`residual`/`raw`/
      `거리행렬`)으로 합쳤다 — 두 번째 지도 패널을 없앤 만큼 4패널이
      정확히 2×2 그리드로 들어간다. 필터·군집 k·이상치 같은 부가 설정은
      우측 상단 ⚙ 토글로 접어 기본 화면을 비웠다. 케이스 검색창은 이벤트
      로그 하나로 합쳐 중복을 없앴다. 1440×900에서 문서 스크롤 905px/900px
      (사실상 없음), 4패널 모두 헤더가 항상 보이는 채로 내용 많은 위젯만
      안쪽 스크롤되는 건 25번 항목의 원칙을 그대로 유지했다.
    - **처음엔 빈 화면 유지**: 업로드/샘플 버튼을 누르기 전엔 `#layout` 자체를
      숨기는 기존 로직(`showEmptyState`/`hideEmptyState`)을 그대로 뒀다 —
      레이아웃을 다시 짜면서 빈 상태 흐름이 깨지지 않았는지 브라우저에서
      직접 리로드해 재확인했다.
    - **배경/글꼴**: `--bg`/`--panel`을 크림색(#f2f0ea)에서 흰색(#ffffff)으로,
      본문 글꼴을 시스템 산세리프에서 Pretendard(jsdelivr CDN, 실패 시
      시스템 산세리프로 자동 대체)로 바꿨다. 이전에 세리프 폰트를 넣었다가
      줄바꿈이 깨졌던 사고가 있어서(README 앞부분 기록) 이번엔 각 단계마다
      브라우저에서 실제 렌더링을 스크린샷으로 확인하며 진행했다 — 문제
      없음을 확인.
    - **색 채널 재계산 (Ch10 근거)**: 배경이 크림색 → 흰색으로 바뀌면 모든
      색의 대비비가 달라지므로, 하드코딩된 색상을 전부 다시 계산했다(파이썬
      스크립트로 WCAG 상대 휘도 공식 직접 계산, 근거는 아래).
      - *범주형(hijack_tool 등, 10.3.1)*: Okabe–Ito(2008) 색맹 안전 팔레트를
        그대로 쓰면 흰 배경 대비 2.2~3.1:1(orange/skyblue/pink/gray)로 얇은
        O/X 마크 선에는 약해서, 색상족은 유지한 채 전체를 20% 어둡게
        일괄 조정 — 흰 배경 대비 전부 3.4:1 이상, 대부분 4.5:1 이상.
      - *군집 윤곽(ColorBrewer Dark2)*: 점 색상과 겹치지 않는 별도 색상족을
        유지하되(10.3.1 "마크 유형별로 다른 컬러맵") 15% 어둡게 조정 — 전부
        4:1 이상.
      - *심각도(critical~low)*: 순서형(ordinal) 속성이므로 10.3.2 sequential
        colormap 규칙대로 다시 설계했다 — critical→high→medium은 단일
        색조(red) 안에서 휘도가 단조 감소하는 순차형 램프(대비 10.33:1 →
        6.42:1 → 3.76:1), low는 "위험도가 낮다"가 아니라 "위험 척도 자체가
        아니다"라는 별도 범주라 색조를 바꿔 중립 회청(5.98:1)으로 분리했다
        — 무지개 컬러맵의 "hue엔 암묵적 순서가 없다"는 문제(10.3.2)를
        avoid하면서도, SOC 대시보드의 강한 관례(critical=빨강 계열)를
        Ch10.3.4가 언급하는 "강한 도메인 관례는 수용"에 따라 유지했다.
      - *거리 행렬*: `d3.interpolateBlues` 단일 색조 순차형을 그대로 유지
        (이미 10.3.2 부합, 변경 불필요 — 확인만).
      - *투명도*: 데이터 채널로 쓰지 않고 선택/비선택 두 단계로만 쓰는
        기존 원칙(10.2.4) 유지.

28. **채널을 방어 성공/실패(모양)와 군집(색) 딱 두 개로만 쓰도록 더 줄이고,
    속성 지도에서 UMAP 산점도 밖의 모든 것(범례·캡션·미니차트·군집
    특성표·군집 검증표)을 없앴다. "샘플로 초기화"도 없애 실제 업로드
    없이는 아무 결과도 안 뜨게 했다.**
    - **색-기준 드롭다운 삭제** — 점 색깔을 심각도/성공실패/납치도구 등으로
      바꿔 보던 `#color-by`를 없앴다. 이제 점은 항상 같은 중립색
      (`POINT_STROKE`)이고, 모양(O=방어 성공/X=뚫림)만 인코딩한다. 색은
      군집 윤곽선(Dark2 팔레트)에만 남아 채널이 완전히 분리된다(5장 채널
      랭킹 + 6.9). 색-기준에 종속돼 있던 `colorScaleFor`/`colorValue`/
      `labelForField`/`labelForValue`/범례/미니차트 클릭 필터(`toggleAttrFilter`)
      전부 죽은 코드라 같이 지웠다.
    - **속성 지도 패널을 UMAP만 남기고 비움** — 범례(`legend-box`), 브러시
      선택 결과 문구(`brush-summary`), 속성뷰 클릭 필터 목록(`attr-selection`),
      "군집 특성" 표(`cluster-summary` UI), 4개 미니 차트, "군집 검증"
      ARI/순도 표를 모두 지도 패널에서 뺐다. 브러시로 드래그해서 영역
      선택하는 기능 자체는 남겨뒀다 — 선택된 점만 남기고 나머지를 흐리게
      하는 시각적 피드백(지도 위 자체)만으로 충분하고, 텍스트 요약 박스가
      없어도 동작한다. 군집별 대표 사례(★) 표시는 지도 위 오버레이라
      "설명 문구"가 아니므로 유지, 계산 함수(`computeClusterSummary`)도
      그대로 남겨뒀다.
    - **"샘플로 초기화" 제거** — 상단 바의 샘플 리셋 버튼과 빈 화면의
      "샘플 데이터로 체험하기" 버튼, 관련 `/api/reset` 호출 경로를 프론트
      엔드에서 전부 없앴다. 이제 화면에 뭔가 뜨는 유일한 경로는 실제
      trace JSON을 업로드하는 것뿐이다 — 빈 상태 로직(`showEmptyState`/
      `hideEmptyState`) 자체는 이미 "업로드 전엔 아무것도 안 뜬다"로
      돼 있었으므로 건드리지 않고 그대로 재사용했다.
    - 리팩터 후 브라우저에서 콘솔 에러 없이 지도 3개 탭(residual/raw/거리행렬)
      전환, 조건 필터, 케이스 선택→TRACE/ANALYSIS VIEW, 지도 설정(⚙) 패널이
      모두 정상 동작하는지 직접 확인했다.

29. **점 색상을 방어 성공/실패(초록/빨강)로 되돌림 — "군집에만 색"은 군집
    윤곽선 얘기였는데 점 자체까지 무채색으로 만들어버린 게 과잉 적용이었다.**
    이제 O(방어 성공)는 초록(`#2f6b4a`), X(뚫림)는 빨강(`#7a2a20`)이고, 군집
    윤곽선은 여전히 별도 팔레트(Dark2)다. 모양과 색이 같은 속성(방어 성공/실패)을
    가리키는 중복 인코딩(redundant encoding, 5장)이라 서로 충돌하지 않는다 —
    군집 색(윤곽선)과 방어 결과 색(점)은 채도·마크 종류가 달라 시각적으로
    분리된다.

30. **1장(What's Vis, and Why Do It?)을 기준으로 프로젝트 전체를 what-why-how
    분석 프레임워크로 다시 점검** — 1.14절의 핵심 주장은 "복잡한 vis 사용은
    단일 분석으로 끝나지 않고, 한 인스턴스의 출력이 다음 인스턴스의 입력이
    되는 연쇄(chained sequence)로 분석해야 한다"는 것이다. DojoScope를 이
    틀에 맞춰 명시적으로 점검한 결과:
    - **인스턴스 1(개요)** — What: 파생 데이터(residual DTW distance 기반
      UMAP 2D 좌표 + 계층적 군집) / Why: 발견(discover) — 행동이 비슷한
      케이스 군집·이상치를 찾는다 / How: 산점도(위치=UMAP 좌표), 방어
      성공/실패는 모양+색 중복 인코딩, 군집은 윤곽선 색.
    - **인스턴스 2(원문, 인스턴스 1의 클릭 출력이 입력)** — What: 선택된
      케이스의 원본 이벤트 시퀀스 / Why: 제시/식별(present, identify) — 그
      트레이스에서 실제로 무슨 일이 있었는지 확인 / How: TRACE VIEW 리스트,
      시간 순서=행 위치, 주입 여부=배지.
    - **인스턴스 3(이웃 근거, 인스턴스 1의 단일 선택이 입력)** — What: 선택된
      케이스와 가장 가까운 4건 + 실제 거리값 / Why: 설명(explain) — "왜
      이 위치에 있는지"를 검증 가능한 숫자로 제시(XAI, README §26) / How:
      막대 차트(길이=거리), 클릭하면 인스턴스 4로 연쇄.
    - **인스턴스 4(DTW 비교, A+B 두 선택이 입력)** — What: 파생 데이터(DTW
      정렬 경로 + 거리) / Why: 비교(compare) — 두 트레이스가 왜/어디서
      갈라지는지 확인 / How: ANALYSIS VIEW 정렬 셀 + 스크럽바.
    - **인스턴스 5(이벤트 로그, KPI의 심각도 클릭이 입력이 될 수 있음)** —
      What: 전체 케이스 테이블 / Why: 검색/위치 찾기(locate) — 특정 심각도나
      case_id를 찾는다 / How: 페이지네이션 테이블, 행 클릭 시 인스턴스 2·3·4로
      연쇄.
    - 이 점검으로 확인한 것: 각 패널이 독립된 "여러 개의 작은 도구"가
      아니라 클릭/선택이 다음 패널의 입력이 되는 하나의 연쇄로 실제
      동작하고 있었다(설계가 이미 이 틀에 맞았다) — 그래서 1장을 근거로
      코드를 고친 부분은 없고, 이 연쇄 구조를 README에 명시적으로 문서화한
      것 자체가 점검 결과다.
    - **점검 중 발견했지만 이번엔 고치지 않은 것 (1.13 change blindness)**:
      조건 필터(전체/A/B)를 누르면 `filteredCases()`가 배열에서 케이스를
      아예 제거해버려서, 지도 위 점들이 자리를 유지한 채 옅어지는 게 아니라
      갑자기 사라진다 — 1.13절이 경고하는 "다른 곳에 주의를 두면 큰 변화도
      놓친다"는 change blindness에 정확히 해당하는 상황이다. 근본적으로
      고치려면 지금처럼 매 렌더링마다 SVG를 통째로 지우고
      다시 그리는 구조(`svg.selectAll('*').remove()`)를 점진적 갱신(enter/
      update/exit + d3 transition)으로 바꿔야 하는데, 줌·브러시·군집
      윤곽까지 얽혀 있어 이번 턴 범위를 넘는 구조 변경이라 판단해 보류했다
      — 다음에 다룰 항목으로 남겨둔다.

31. **"군집이 멀리 있는 점까지 붙잡는다" 문제 — 원인은 알고리즘이 아니라
    볼록 껍질(convex hull)을 잘못된 공간에 그린 것이었다** — 계층적 군집화
    자체(average-linkage, 잔차 DTW 거리행렬, 결정적 알고리즘)는 항상 하나로
    고정돼 있었고 바뀐 적이 없다(`pipeline/cluster.py`). 문제는 UMAP이 원래
    거리를 "국소 이웃"만 최대한 보존하며 2D로 누르는 별개의 투영이라, 같은
    군집의 구성원이 2D에서 여러 덩어리로 흩어질 수 있다는 데 있었다 — 이때
    군집 전체에 볼록 껍질 하나만 씌우면, 흩어진 두 덩어리 사이의 빈 공간에
    있는 **다른 군집의 점**까지 껍질 안에 걸려서 "멀리 있는 걸 붙잡는" 것처럼
    보인다. 실제로 UMAP 좌표를 직접 계산해서 확인함: banking suite k=6에서
    4번 군집(중심 (2.70,12.74))과 5번 군집(중심 (3.03,11.39))의 중심간 거리가
    각 군집의 평균 반경(0.8 안팎)과 비슷할 만큼 가까워서, 볼록 껍질을 그대로
    씌우면 겹칠 수 있는 상황이 실제로 있었다.
    **수정**: 군집 전체에 볼록 껍질 하나를 씌우는 대신, 화면 픽셀 거리 기준
    "실제로 서로 붙어 있는" 부분집합(연결 요소, connected components)별로
    각각 작은 볼록 껍질을 그리게 했다(`drawHulls()`/`connectedComponents()`,
    `frontend/app.js`). 문턱값은 고정 픽셀이 아니라 현재 화면에 보이는 모든
    점의 최근접 이웃 거리 중앙값의 2.5배로 잡아서, 확대/축소하거나 필터로
    점 개수가 바뀌어도 "가깝다"의 기준이 데이터 밀도에 맞춰 같이 조정된다.
    브라우저에서 확대해 직접 확인: 수정 전엔 떨어진 두 X 표시 사이를 가로질러
    빈 공간을 뒤덮던 껍질이, 수정 후엔 실제로 붙어 있는 3~4개 점끼리만 작게
    감싸고 그 사이 무관한 점은 감싸지 않는 것을 확인했다.

32. **UMAP이 같은 데이터에 대해 항상 같은 좌표를 내는지 재검증** — `/api/reset`을
    세 번 독립적으로 다시 실행해(임베딩 재적합→DTW 재계산→UMAP 재투영→군집
    재계산 전 과정을 처음부터 다시 돈다) banking suite 48건의
    `coords_residual`을 비교했다. 결과: **최대 오차 0.0, 평균 오차 0.0** —
    소수점까지 완전히 동일. `random_state=42`+`n_jobs=1`(UMAP)과
    `random_state=self.seed`(TF-IDF→SVD 임베더)가 이미 고정돼 있고, 여기에
    §27~29에서 고정한 정확한 라이브러리 버전(`numpy==2.4.4` 등)까지 더해지면
    같은 데이터→항상 같은 결과가 보장된다는 걸 가정이 아니라 직접 재현해서
    확인했다.

33. **군집별 선택 UI 추가** — 속성 지도 패널에 "전체 / 군집 0 (1) / 군집 1
    (14) / ..." 칩 목록을 추가했다(`renderClusterPicker()`). 색은 지도 위
    군집 윤곽선과 같은 팔레트를 그대로 써서 "이 칩 = 저 색 윤곽선"이 바로
    보이게 했고, 클릭하면 그 군집만 남기고 나머지를 흐리게 한다(기존 브러시
    하이라이트 메커니즘 재사용이라 점이 사라지지 않고 옅어지기만 함 —
    §25/30 원칙 유지). 군집 k 슬라이더를 바꾸거나 브러시로 새로 선택하면
    군집 번호 의미가 달라지므로 자동으로 선택이 풀린다.

34. **군집 분석 — 무엇이 비슷해서 묶였는지, 같은 군집 안의 차이, 실제 검증**
    (banking suite, 48건, k=6 — 위 §32에서 재현성 검증까지 마친 데이터로
    다시 확인) 트레이스 원문을 직접 대조한 결과:
    - **비슷한 점**: 거의 모든 군집이 결국 `send_money`를 같은 공격자 계좌
      (`UK1234567890`)로 보내는 걸로 끝난다. 군집을 실제로 가르는 건 "어떤
      도구가 뚫렸는지"가 아니라 **주입된 지시문을 읽은 뒤 송금 전까지 거치는
      조회 단계의 개수·종류**다 — 군집 1(14건)은 조회 없이 바로
      `read_file→send_money`, 군집 5(11건)는 `get_iban` 또는
      `update_password` 한 번, 군집 3(9건)은 거래내역/예약거래 조회, 군집
      4(8건)는 여러 조회를 한꺼번에(전부 A조건), 군집 2(5건)는 예약거래
      확인. `get_iban`과 `update_password`처럼 서로 다른 도구도 "짧은 조회
      한 번 + 송금"이라는 시퀀스 길이·리듬이 같으면 같은 군집으로 묶인다.
    - **같은 군집 안의 차이**: (1) 방어 성공/실패가 군집을 안 가른다 — 군집
      5 안에 조건 A 4건, B 7건이 섞여 있고 B(방어)인데도 뚫린 경우가
      다수라, 행동 모양이 같은 공격을 지금 방어 로직이 일관되게 막지 못한다는
      뜻. (2) 뚫린 도구 정체(`get_iban` vs `update_password`)가 군집
      안에서 섞인다 — 실제 피해 내용은 다른데 시퀀스 모양이 같아서 한
      군집. (3) 가장 큰 군집(1번)은 실제 위험(수신자=공격자 계좌, 11건)과
      정상 송금(수신자=정상 계좌로 추정, 3건)이 섞여 있다 — 시퀀스 모양만
      으로는 진짜와 가짜 송금을 못 가르는 게 이 방식의 실제 한계.
    - **검증**: 위 세 가지를 주장으로 남기지 않고 각 군집의 `send_money`
      수신자·호출된 함수 조합·조건·판정을 코드로 직접 집계해서(스크립트로
      전수 조사, 표본 아님) 표로 확인했다 — 화면에서도 군집 칩(§33)을 눌러
      해당 군집만 남긴 뒤 이벤트 로그·TRACE VIEW로 개별 케이스 원문을 같은
      방식으로 재확인할 수 있다.

## 시각 인코딩 설계 근거 (Visualization Analysis and Design 적용)

Tamara Munzner의 *Visualization Analysis and Design*(2014)을 기준으로 다음
결정을 내렸다 — 각 장 번호는 그 책의 장이다.

- **위치(공간)가 가장 효과적인 채널**(5장 채널 랭킹)이므로, UMAP 좌표를 담는
  지도가 항상 화면에서 가장 큰 자리를 차지한다. 그중에서도 **residual 공간을
  기본(primary) 뷰로 삼았다** — 군집 검증(ARI)에서 hijack_tool을 raw보다 residual이
  더 잘 구분해내는 경향이 있기 때문("방어 개발자에게 가장 중요한 질문 = 이
  트레이스가 어떤 공격 패턴에 속하는가"). raw는 "정답 이탈 전 전체 궤적"이라는
  다른 정보를 주는 보조 뷰로 남긴다.
- **모양(shape)과 색상(color hue)을 서로 다른 역할로 분리했다**(5.4 표현성/효과성
  원칙). 모양은 식별 채널 중 색상보다 약하지만(5.4.2 랭킹) 이진 판단에는
  충분하고, "항상 같은 뜻"으로 고정해 두면 범례를 안 봐도 읽힌다 — 그래서
  **모양=방어 결과(O 방어/X 뚫림, 절대 안 바뀜)**로 고정하고, **색상=색상
  기준 드롭다운(과제 성공/실패, 군집, 납치 도구 등 탐색적으로 바꿔가며 볼 수
  있는 속성)**으로 완전히 분리했다. 예전 버전은 판정(verdict) 하나를 색 4단계로
  뭉뚱그렸는데, 이는 두 개의 서로 다른 이진 사실(방어됐는가, 과제가
  성공했는가)을 한 채널에 욱여넣은 것이라 두 채널로 풀었다.
- **투명도(transparency)는 독립적인 데이터 인코딩 채널이 아니다**(10.2.4) — 다른
  색 채널(특히 채도·명도)과 강하게 간섭해서 "그 자체로 어떤 속성"을 나타내는
  용도로 쓰면 안 되고, 전경/배경을 가르는 이진 용도(예: 선택됨/선택 안 됨)에만
  안전하다. 예전 Control Panel의 "투명도 조절" 슬라이더는 어떤 속성과도 결합되지
  않은 채 전체 점에 걸리는 장식적 값이라 존재 이유가 없었다 — 제거하고, 대신
  isolation percentile(이미 계산되어 있던 kNN 거리 기반 이상치 지표)을 이진
  강조(상위 10% only)에 쓰는 **"이상치 후보만 강조"** 토글로 바꿨다. 이건 진짜
  데이터에 결속된 필터이자 정확히 투명도가 허용되는 "전경/배경 구분" 용법이다.
- **거리 행렬(클러스터 히트맵)**은 다대다 거리 비교를 위한 표준 idiom(7.5.2)이다
  — 지도(산점도)는 두 케이스의 "관계"를 한눈에 보여주는 데 약하므로(위치가
  가깝다/멀다 정도만), 정확한 거리 값이 필요한 작업에는 정렬된 행렬이 맞는
  선택이다.
- **선택 강조는 색을 바꾸지 않고 외곽선(outline)으로 표시한다**(11.4.2
  Highlighting) — 색을 바꿔버리면 기존 색상 인코딩이 가려지기 때문에, A/B로
  고른 케이스는 파란/빨간 외곽 원으로만 표시해 원래 색·모양 정보를 유지한다.
- **두 지도는 같은 색상 인코딩을 공유하는 multiform 뷰**(12.3.1 Share Encoding)로
  연결되고, 브러시 결과가 두 뷰에 동시에 반영되는 **linked highlighting**(12.3.1)으로
  "한 공간에서 뭉친 점들이 다른 공간에서 어떻게 흩어지는지" 비교할 수 있다.

## 파이프라인 알고리즘 — 최근 실험(pipeline_study) 반영

기존 프로젝트 디렉터리의 `pipeline_study/`(k-sweep·weighted purity·medoid 실험)와
`security_dashboard/`(residual-우선 결론)의 결과를 backend 파이프라인에 반영했다.

- **군집 개수 k 자동 선택** (`pipeline/cluster.py::select_k_by_silhouette`) —
  예전엔 k=6 고정이었다. `pipeline_study`는 k-스윕으로 ARI가 가장 높은 k를
  찾았지만, 그건 검증에 쓸 라벨(hijack_tool)을 k 선택에도 쓰는 순환 논리라
  ARI/NMI를 "정직한 검증 지표"로 화면에 보고하는 이 프로젝트에는 그대로 못
  가져왔다. 대신 **라벨을 전혀 쓰지 않는 실루엣 계수**가 가장 높은 k를 raw/residual
  공간마다 독립적으로 고르고, k-스윕 표 전체를 화면(군집 검증 패널 하단)에 그대로
  노출해 어떤 k들을 검토했는지 투명하게 보여준다.
- **weighted purity 지표 추가** (`cluster_agreement`) — ARI/NMI에 더해, "군집
  하나를 열어보면 실제로 몇 %가 기대한 라벨(예: 같은 hijack_tool)인가"를
  케이스 수로 가중평균한 순도를 함께 보여준다(작은 군집이 순도를 착시적으로
  끌어올리는 문제는 "군집 개수 평균"이 아니라 "케이스 수 가중평균"으로 피한다 —
  `pipeline_study/study_pipeline.py`의 `weighted_purity`와 동일한 정의).
- **군집 대표 사례(medoid)** (`compute_medoids`) — 군집 중심을 벡터 평균(가상의
  점)이 아니라, 같은 군집의 다른 모든 점과 거리 합이 최소인 **실존하는 케이스**로
  잡는다. `suite JSON`의 `cluster_medoids`에 군집별 대표 case_id·크기·대표
  납치 도구가 들어 있다(`pipeline_study/umap_projection.py`의 개념 이식).
- **거리 행렬 노출** — 클러스터링에 쓰고 버려지던 raw/residual pairwise DTW
  거리 행렬을 `suite JSON`의 `distance_matrix`에 그대로 실어, 화면의 클러스터
  히트맵이 재계산 없이 바로 그릴 수 있게 했다.

## PPT에서 발견한 분석 패턴을 이 화면에서 재현하기

`dojoscope_26.09.15_임정윤.pptx`/`군집화_알고리즘_피드백_확인.pptx`는 banking
suite에서 get_iban 탈취 8건이 왜 3개 군집으로 흩어졌는지를 (1) 군집 배정 CSV
확인 → (2) 원본 이벤트 시퀀스 직접 열람 → (3) 같은/다른 군집 나란히 비교, 세
단계로 손으로 파고들어 "공격 시그니처(get_iban→send_money)는 동일하지만
정상 조회 도구가 끼어드는 정도가 군집을 가른다"와 "군집 안에서도 get_iban의
`recipient` 파라미터 하나로 탈취/방어가 갈린다"는 두 가지를 알아냈다(슬라이드
13-14). 이번 업데이트로 이 워크플로 전체가 화면 안에서 가능해졌다:

1. **좌측 속성 뷰**에서 "납치 도구" 막대의 get_iban을 클릭 → 해당 케이스들만
   지도에서 강조되고 목록으로 나열된다(1단계 대체).
2. 목록에서 케이스를 클릭하면 **트레이스 원문**에 함수·인자·응답 텍스트가 그대로
   펼쳐진다 — `recipient=...` 같은 결정적 파라미터가 바로 보인다(2단계 대체).
3. 거리 행렬(클러스터 히트맵)이나 지도에서 두 케이스를 골라 **비교 도구**로
   나란히 놓으면 GT/A/B 3단 정렬 + 스크러버로 "어디서부터 달라지는지"를 스텝
   단위로 확인할 수 있다(3단계 대체).

다만 "이 파라미터가 결정적이었다"는 마지막 해석 자체는 여전히 사람이 원문을
읽고 판단해야 한다 — 도구 인자값까지 자동으로 GT와 의미 비교해 "이 지점이
결정적 이탈"이라고 자동 표시하는 기능은 다음 확장으로 남겨 두었다(현재
GT 정렬은 함수 호출의 임베딩 유사도로만 판단하고, GT 자체가 인자 정보 없이
"함수 이름"으로만 직렬화되기 때문— README §1.1/§1.4 참고).

## UMAP 좌표가 실행할 때마다 달라 보이던 문제 — 원인과 수정

`dojoscope_26.09.15_임정윤.pptx`/`군집화_알고리즘_피드백_확인.pptx`에 실린 UMAP
이미지와 이 앱이 매번 새로 계산하는 UMAP이 달라 보이는 문제를 재현·확인했다.

- 두 UMAP은 **같은 함수(`pipeline/reduce.py::project_2d`), 같은 거리행렬, 같은
  seed(42)**를 쓴다 — 슬라이드(`security_dashboard가 실제로 쓰는 UMAP 좌표...
  그대로`, feedback 덱 슬라이드15)와 이 앱의 `pipeline/` 모두 `pipeline_study`가
  참조한 동일한 원본을 공유한다. 거리행렬도 직접 비교해 소수점 8자리까지
  일치함을 확인했다(부동소수 오차 수준).
- 그런데도 좌표가 달랐던 이유: `umap.UMAP(random_state=seed)`만 주고 `n_jobs`를
  기본값(-1, 병렬)으로 두면, **seed를 고정해도 numba 병렬 SGD 최적화 단계가
  프로세스마다 다른 스레드 스케줄로 실행돼 실행할 때마다 다른 좌표가 나온다** —
  실제로 같은 스크립트를 두 프로세스로 나눠 실행해 좌표가 달라짐을 재현했고,
  `n_jobs=1`을 주면 완전히 결정론적으로 바뀌는 것(반복 실행·재시작 모두 좌표
  완전 동일)까지 확인했다.
- `pipeline/reduce.py::project_2d`에 `n_jobs=1`을 추가해 수정했다 — 이제 서버를
  몇 번을 재시작해도, 같은 데이터라면 항상 같은 UMAP 좌표가 나온다(직접 검증:
  서버 프로세스를 완전히 새로 띄운 뒤 좌표를 다시 조회해 동일함을 확인).
- 참고로 이 수정으로 재현한 좌표는 `pipeline_study`가 저장해 둔 거리행렬을
  독립적으로 다시 투영한 결과와도 소수점까지 일치했다 — 즉 지금 이 값이
  "가장 최신"이 아니라 애초에 **유일하게 맞는 결정론적 값**이고, 이전에 보였던
  차이는 알고리즘이 다른 게 아니라 실행할 때마다 흔들리던 비결정성이었다.

## 실 AgentDojo 로그 사용하기

`ethz-spylab/agentdojo`의 벤치마크 스크립트(`python -m agentdojo.scripts.benchmark
--logdir runs ...`)는 케이스마다 `runs/<pipeline_name>/<suite_name>/<user_task_id>/
<attack_name>/<injection_task_id>.json` 파일을 남긴다(`agentdojo.logging.TraceLogger`).
이 파일들을 우리 스키마로 변환한다:

```bash
cd backend
python adapters/agentdojo_adapter.py /path/to/runs -o converted.json
curl -F "file=@converted.json" http://<서버>:8000/api/upload
```

### 바로 써볼 수 있는 예시 파일

실제 AgentDojo 로그는 아직 구하지 못했지만(§ 아래 한계 참고), 필드 구조와 의미는
진짜 TraceLogger 출력과 동일한 예시를 만들어 프로젝트에 넣어 뒀다:

- `backend/adapters/example_logs/` — AgentDojo raw 로그 형식 그대로(20개 파일,
  `<pipeline_name>/<suite_name>/<user_task_id>/<attack_name>/<injection_task_id>.json`
  경로 규칙까지 동일). 어댑터 자체를 테스트해보고 싶을 때 사용:
  ```bash
  cd backend
  python adapters/agentdojo_adapter.py adapters/example_logs -o example_converted.json
  ```
- `backend/data/example_upload.json` — 위 로그를 어댑터로 미리 변환해 둔 결과
  (banking·slack 2개 suite, 16케이스). DojoScope 화면 상단 "데이터 업로드"로
  바로 올려서 빈 상태 → 업로드 → 즉시 반영 흐름을 시험해볼 수 있다. 무방어인데
  우연히 막힌 케이스, 방어했는데 뚫린 케이스(퇴행)까지 섞어 둬서 "보안 결과"
  패널의 4분면(차단/퇴행/여전히 뚫림/여전히 안전)이 전부 나온다.

**주의할 점 두 가지** (어댑터 파일 상단 docstring에도 정리해 둠):

1. AgentDojo의 `security` 필드는 우리와 **반대 의미**다(AgentDojo: True=안전,
   우리: True=뚫림) — 어댑터가 반전시켜서 넣는다.
2. 정답 시퀀스(`ground_truth`)는 로그 파일 안에 없다 — AgentDojo가 이걸
   `user_task.ground_truth(pre_environment)`로 그때그때 계산하기 때문이다.
   어댑터는 같은 (suite, user_task)의 **"공격 없음"(`attack_type=="none"`) 기준
   실행**에서 실제로 호출된 도구 이름 순서를 ground_truth로 대신 쓴다 —
   `benchmark_suite_without_injections()`를 먼저 돌려서 기준 로그를 남겨 둬야
   한다. 없으면 경고를 출력하고 해당 (suite, user_task)는 `ground_truth=[]`로
   업로드된다(GT 정렬/잔차 계산은 무의미해지지만 나머지 기능은 정상 동작).

## 처음엔 빈 화면, 업로드해야 실행됨

서버를 처음 띄우면(또는 `backend/data/current_traces.json`이 아예 없으면) 샘플
데이터를 자동으로 채우지 않고 **완전히 빈 화면**("아직 데이터가 없습니다" +
업로드 버튼)으로 시작한다. 업로드하거나 "샘플 데이터로 체험하기"를 눌러야
지도가 계산된다. 한 번 업로드한 데이터는 `current_traces.json`에 저장되므로
그 다음부터 서버를 재시작해도 마지막 데이터셋이 복원된다 — 빈 상태는 정말
"한 번도 아무것도 넣은 적 없는" 경우에만 나타난다.

## 실행 방법

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt

uvicorn app:app --host 0.0.0.0 --port 8000
```

브라우저에서 `http://localhost:8000` 접속. 첫 기동 시 샘플 데이터(4 suite ×
192케이스)를 계산하는 데 UMAP JIT 컴파일 때문에 10~60초 정도 걸릴 수 있다(그
이후 요청은 메모리 캐시를 쓰므로 즉시 응답한다).

### 새 데이터 업로드

화면 상단 "데이터 업로드" 버튼으로 trace JSON 파일(`pipeline/schema.py`의
`Trace`/`Event` 형식을 따르는 배열, 또는 `{"cases": [...]}`)을 올리면 서버가
기존 데이터와 `(suite, user_task_id, injection_task_id, condition)` 키로
병합하고 전체를 재계산한다. 완료되면 화면이 자동으로 새 데이터로 갱신된다.
"샘플로 초기화" 버튼으로 언제든 합성 샘플 데이터로 되돌릴 수 있다.

실제 AgentDojo 로그가 있다면 아래 "실 AgentDojo 로그 사용하기" 절의 어댑터로
변환한 뒤 그대로 업로드하면 된다.

## 외부에서 링크로 접속 가능하게 하기 (Docker)

`docker-compose.yml`로 nginx(정적 프론트엔드 서빙 + `/api/*` 리버스 프록시)와
FastAPI 백엔드를 분리된 컨테이너 두 개로 띄운다 — 팀에서 받은 참고 배포
설정(`docker-setting-file.zip`, Vite+nginx+백엔드 컨테이너 구조)과 같은
패턴이되, DojoScope의 frontend/는 번들러가 없는 순수 정적 파일이라 그
참고 파일에 있던 node 빌드 단계는 뺐다.

```bash
# 서버에서
cd dojoscope-app
docker compose up -d --build
```

- **외부 접속 포트: 18240** (`.env`의 `HOST_WEB_PORT`) — `http://<서버 IP>:18240`.
  참고로 받은 파일의 포트(18080/8080/5001)와도, nginx/uvicorn 기본값(80/8000)과도
  겹치지 않게 골랐다. 서버 방화벽/보안 그룹에서 18240번 인바운드를 열어줘야
  실제로 접속된다 — docker-compose가 포트를 publish하는 것과 OS/클라우드
  방화벽을 여는 것은 별개다.
- 내부적으로는 nginx가 7680번에서 듣고 `/api/*`만 백엔드 컨테이너(7601번,
  호스트에는 노출 안 됨)로 넘긴다. 백엔드는 `backend/Dockerfile`, 프론트는
  루트 `Dockerfile` + `docker/nginx.conf`.
- 업로드된 데이터(`backend/data/current_traces.json`)는 `./backend/data`를
  볼륨으로 마운트해뒀으므로 컨테이너를 내렸다 올려도 유지된다.
- 이미지/포트를 바꾸고 싶으면 `.env`의 `HOST_WEB_PORT`, `DOJO_BACKEND_IMAGE`,
  `DOJO_WEB_IMAGE`만 고치면 된다.

Docker 없이 그냥 uvicorn으로 직접 띄우고 싶다면 "로컬 실행" 섹션 그대로
`--host 0.0.0.0`으로 바꿔서 실행해도 된다(포트를 직접 열거나 리버스 프록시로
연결).

## 프로젝트 구조

```
dojoscope-app/
├── backend/
│   ├── app.py            # FastAPI: /api/manifest, /api/suite/{name}, /api/upload,
│   │                      #   /api/reset, /api/compare(임의 두 케이스 DTW), /api/search
│   ├── store.py           # 메모리 상태(현재 trace 목록·계산 결과·임베더) + 디스크 영속화
│   ├── pipeline/           # 임베딩·DTW·GT정렬·UMAP·군집화(k자동선택+medoid+weighted purity)·검증
│   ├── adapters/
│   │   └── agentdojo_adapter.py   # 실 AgentDojo TraceLogger 로그 -> 우리 스키마 변환
│   ├── data/
│   │   ├── sample_traces.json     # 합성 샘플(4 suite × 192케이스, --reset 기준)
│   │   └── current_traces.json    # 런타임에 생성되는 "현재 데이터셋" (gitignore 권장)
│   └── requirements.txt
└── frontend/
    ├── index.html / styles.css / app.js   # 4분할 레이아웃, D3 기반 시각화 (빌드 불필요)
```

## 한계

- 샘플 데이터는 실제 AgentDojo 로그가 아니라 합성 데이터다(파이프라인 동작
  검증용). 실 로그 어댑터를 작성해 업로드하면 그대로 반영된다.
- 기본 임베딩 백엔드는 오프라인에서도 동작하는 TF-IDF+SVD(LSA)다.
  `requirements-embedding.txt`(원본 프로젝트 참고)를 추가 설치하면 실제
  transformer 임베딩(bge-small)으로 전환할 수 있다.
- 업로드 후 재계산은 동기적으로 처리된다(요청이 끝날 때까지 대기) — 데이터가
  아주 커지면 비동기 작업 큐로 바꾸는 것을 다음 확장으로 고려할 수 있다.
- `suite JSON`에 raw/residual 거리 행렬을 통째로 싣기 때문에(클러스터 히트맵용)
  suite당 케이스 수가 수백 건을 넘어가면 응답 크기가 n² 로 커진다 — 지금
  규모(suite당 수십~백여 건)에서는 문제없지만, 훨씬 큰 데이터셋이면 히트맵을
  별도 엔드포인트로 분리해 지연 로딩하는 편이 좋다.
- 실 AgentDojo 로그 어댑터는 assistant의 "최종 텍스트 답변"(tool_call이 없는
  메시지)을 이벤트 시퀀스에서 제외한다 — 우리 스키마의 역할(role)이 user/
  tool_call/tool_resp 세 가지뿐이라 대응점이 없기 때문이다. 어떤 도구를 어떤
  순서로 불렀는지가 이 프로젝트의 핵심 신호이므로 실용적으로는 충분하지만,
  텍스트 답변 자체의 내용을 비교해야 하는 분석에는 부족하다.
